# A third internal implementation: Java, written from the kit alone (2026-11-17)

**This is not an outside implementation.** It was written by an AI agent that this project started, inside the same
session. It adds a third language to Go and Rust, and it tests how well the kit reads for someone who has never seen
the Python or Node code. It does not show that a team outside this project can implement UAI-1.

## How it was run

- The agent was given a directory holding only the kit: `docs/interop/UAI-1.md`, `SECURITY_PROFILES.md`, the implementer
  README, `contracts/uai1/` (schema, error registry, suite, runner) and the two vector files. No Python, Node or CNS code.
- It used JDK 21 and nothing else. The JDK's Ed25519 is more lenient than the spec, so the strict rules are written out
  in `Ed25519Strict.java`.
- Scope: the "minimal implementation" steps 1 to 6 of `docs/interop/implementers/README.md`. Session, disclosure, acting,
  endorsement and revocation are not implemented. Only pinned trust is.
- Checks made afterwards: all 21 of the agent's tool calls were read and none named another repository or the reference
  code; the adapter was rebuilt from the committed source and the suite rerun (below).

## Result

| Check | Result |
|---|---|
| Conformance suite | 72 of 72 (71 specification, 1 reference), 0 failed, none skipped |
| Digest vectors | 38 of 38 |
| Signed envelopes in `uai-vectors.json` | 3 of 3 (digest, signing digest, strict signature) |
| Digest refusals with a JSON form | 5 of 5 refused. `non_text_key` and `bytes` cannot be written in JSON and were not tested |

Not run: the suite against a deliberately weakened verifier, cofactor edge cases, a non-canonical `R` beyond what the suite
holds. The JDK's own Ed25519 accepts the `reject-small-order-key` case, so the strict rules in this code do real work.

Reproduce, from the repository root:

    sh interop/independent/java/build.sh
    python3 contracts/uai1/run_conformance.py --cmd "java -cp interop/independent/java/out Adapter"
    java -cp interop/independent/java/out SelfTest .

## Faults found in the kit (none fixed in this change)

1. **Suite: `oversized-message` and `deeply-nested-value` do not test what their names say.** Both are non-envelope
   objects, so they are refused as `malformed` for missing fields. The 1 MiB and depth rules are never exercised, and
   section 2 does not decide them either.
2. **Suite and runner: the digest in `{"accept": {"digest": ...}}` is never checked,** and the guide does not say which
   digest it is. This implementation returns the digest of the whole envelope including `sig`, which matches the vectors.
3. **Suite: nesting is tested with maps only,** never with lists as levels.
4. **Suite: check order is untested.** Every case has a single defect, so expired versus untrusted versus audience, untrusted
   before replayed, and signature before not-yet-valid are never distinguished.
5. **Guide: wrong cross-references.** It says "33 cases" in its closing section against 72 elsewhere, and names files that
   are not in the kit (`interop/conformance/reference_adapter.py`, `docs/EVIDENCE.md`). The runner's docstring points to a
   `README.md` beside it that does not exist.
6. **Spec: a trap in the digest.** Float rendering is "Python repr". JDK 21 `Double.toString(Double.MIN_VALUE)` gives
   `4.9E-324` where the vector wants `5e-324`. The first attempt matched 37 of 38 vectors until the fewest digits that read
   back exactly were computed.

## Sentences the implementer found ambiguous, even where the suite passed

Each is a place where a second reader could choose differently. The choice made here is in brackets.

1. Reader versus check order: a `v: uai/2` message with a float in `body` gets `profile`, not `version` [floats and large
   integers are refused anywhere in the document before the field and version checks].
2. A `v` that is not text [`malformed`].
3. Session lifetime ("must expire, and may claim at most 24 hours"), a missing endorsement expiry, and the 8-endorsement and
   64-capability limits name no refusal code [`malformed`; the suite never exercises them].
4. Body shape per kind: sections 4 and 5 give exact shapes, but a valid `request-0` has only `{"capability","version"}`
   [body shape is not validated per kind].
5. "Strict" Ed25519 does not say cofactored or cofactorless, or whether a small-order `R` is allowed [cofactorless; canonical
   `A` and `R`; `s` below the group order; small-order `A` refused; a canonical small-order `R` is not refused].
6. `to` is `""` while an audience is set [`audience`].
7. `trust: null` and `kinds: null`, and whether a refusal spends the ledger [null means no restriction, `[]` means nothing
   accepted, the ledger is spent only on accept].
8. JSON details: `-0` [integer 0]; raw control characters in strings and a form feed as whitespace [`malformed`]; a nesting
   cut-off [20,000 levels, then `malformed`].
9. "The envelope without `sig` (with `v`)" [every field except `sig`].
10. Section 2 never defines "this step" for `kind`.

## What would close each gap

Items 1 to 5 under "Faults" are small edits to the suite, runner and guide. Item 6 is a one-line note in the spec. The
ambiguities are decisions for the spec's owner: each needs one sentence and, where it matters, one suite case.
